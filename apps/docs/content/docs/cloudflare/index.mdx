ZBSearch Edge is a **self-hosted** search API that runs on **Cloudflare Workers** with **R2** as durable storage. It uses the same ZBSearch engine you already know from the browser and Node.js, but exposes it over HTTP with a write buffer and background rebuild pipeline optimized for edge deployments.

This is **not** a managed SaaS product. You deploy the Worker and R2 bucket to your own Cloudflare account. There is no control plane, billing integration, or vendor lock-in beyond standard Cloudflare infrastructure.

## What you get

| Capability | Details |
| --- | --- |
| **Search modes** | Full-text, vector, and hybrid search (same engine as `zbsearch`) |
| **REST API** | Create indexes, upsert/delete documents, search, rebuild, status |
| **Edge latency** | Queries served from Workers close to your users |
| **Durable storage** | Immutable snapshots and a write-ahead buffer in R2 |
| **Background rebuilds** | In-Worker cron for small indexes, or external builder for production |
| **OSS & free to deploy** | Apache 2.0 - you only pay Cloudflare usage |

## Architecture

Writes and reads follow different paths by design. Search always reads a **single immutable snapshot**; writes append to a **buffer** and are merged on rebuild.

```
Client                    Cloudflare Worker                 R2
  │                              │                          │
  │  PUT /documents/:id          │                          │
  │ ───────────────────────────► │  append NDJSON segment   │
  │                              │ ────────────────────────► │
  │  ◄── 202 buffered            │                          │
  │                              │                          │
  │  POST /rebuild (or cron)     │  read snapshot + buffer  │
  │ ───────────────────────────► │ ◄──────────────────────► │
  │                              │  write new snapshot      │
  │                              │ ────────────────────────► │
  │  POST /search                │  load snapshot (cached)  │
  │ ───────────────────────────► │ ◄──────────────────────► │
  │  ◄── 200 hits                │                          │
```

### Packages in the monorepo

| Package | Role |
| --- | --- |
| `@zbsearch/edge-core` | REST router, buffer, rebuild logic, search orchestration |
| `@zbsearch/runtime-cloudflare` | Workers entrypoint, R2 adapter, Workers Cache |
| `@zbsearch/storage-s3` | S3-compatible driver for R2 (used by the rebuild CLI) |
| `@zbsearch/edge-index-builder` | CLI to rebuild indexes from outside the Worker |

Deploy templates live under [`deploy/cloudflare/`](https://github.com/micheleriva/zbsearch/tree/main/deploy/cloudflare) in the repository.

## When to use this

ZBSearch Edge fits when you want:

- A **globally distributed** search API without running your own servers
- **Predictable read performance** (single snapshot per query, no query-time merge)
- **Infrequent or batched writes** with acceptable eventual consistency (seconds to minutes, depending on rebuild schedule)
- **Full-text, vector, or hybrid** search with the same schema model as standalone ZBSearch

For purely local or single-process use cases, use the [`zbsearch`](/docs/zbsearch-js) library directly. Edge adds HTTP, persistence, and the buffer/rebuild pipeline on top.

## Quick start

If you already have a Cloudflare account and Wrangler installed:

```bash
# From the zbsearch monorepo root
wrangler r2 bucket create zbsearch-edge
pnpm deploy:edge
```

After deploy, Wrangler prints your Worker URL. See [Setup](/docs/cloudflare/setup) for the full walkthrough including R2 API tokens, optional auth, and rebuild configuration.
