---
title: ZBSearch vs Orama
description: Head-to-head performance and search-quality benchmarks comparing ZBSearch and Orama on the same workloads.
---

ZBSearch is a fork of Orama maintained by the original engineering team. The API is compatible, but the internals have been optimized - including an explicit **postings list** inverted index that lowers memory use and serialized bundle size while keeping search fast, a faster full-text insert path, and an optional **IVF** vector index. This page summarizes benchmark results from the [`benchmarks/`](https://github.com/micheleriva/zbsearch/tree/main/benchmarks) suite in this repository.

<Callout title="Test environment">
Results below were collected using **Orama 3.1.18** and **ZBSearch 4.0.2** on **November 2, 2026** (Node v26.12.0, Apple Silicon), via [Benny](https://github.com/caderek/benny) for throughput, isolated Node.js processes (`--expose-gc`) for memory, and the BEIR harness for search quality. Higher **ops/s** is better. Percentages show how much slower the loser is relative to the winner in each suite.
</Callout>

## Summary

| Area | Verdict |
| --- | --- |
| Full-text search | ZBSearch is **46–76% faster** on search (1.9–4.2× Orama's throughput); indexing is **~60–62% faster** (~2.5×) |
| Search quality (BEIR) | ZBSearch scores **2× Orama's macro nDCG@10** (0.437 vs 0.222) at **16× lower query latency** |
| Facets | ZBSearch is **65–75% faster** across all facet scenarios (2.9–4.0× Orama's throughput) |
| Vector search | ZBSearch is **11–32% faster** on flat indexes; **IVF** reaches **3.6–6.5×** Orama's throughput |
| Geosearch (BKD) | ZBSearch is up to **~76× faster** on tight-radius queries |
| Sorted indexes (AVL) | ZBSearch is **faster on every** AVL operation (2–56%) |
| Memory footprint | ZBSearch uses **~22% less** heap for the same indexed dataset |
| Persistence size | ZBSearch produces a **42% smaller** serialized index (**35%** smaller gzipped) |
| JS bundle size | **Orama wins**: 22.20 KB vs 30.04 KB min+gzip |

## Core full-text search

Dataset: **1,512** video-game records with `title`, `description`, `rating`, and `genres` fields. Search benchmarks run against a database populated once before timing; insert benchmarks create a fresh database on each iteration.

| Benchmark | Orama 3.1.18 | ZBSearch 4.0.2 | Difference |
| --- | ---: | ---: | --- |
| Insert | 14.1 ops/s | 36.7 ops/s | ZBSearch **61.6%** faster |
| Insert multiple | 14 ops/s | 35 ops/s | ZBSearch **60.0%** faster |
| Plain search | 33,075 ops/s | 139,880 ops/s | ZBSearch **76.4%** faster |
| Search with filters | 23,756 ops/s | 44,224 ops/s | ZBSearch **46.3%** faster |
| Long text + complex filters | 7,046 ops/s | 27,758 ops/s | ZBSearch **74.6%** faster |

ZBSearch is faster across all search scenarios tested here, with the largest gaps on plain search and long-text queries with complex filters. Indexing is also substantially faster (~**2.5×** Orama) thanks to node-local postings caches and a tighter tokenize/insert path.

## Search quality (BEIR)

Throughput without relevance is meaningless, so ranking quality is measured on standard [BEIR](https://github.com/beir-cellar/beir) collections with official relevance judgments, using exact trec_eval semantics. Both engines run with their own ecosystem's stopwords and stemmer. The published Lucene BM25 nDCG@10 is shown as a reference point.

| Dataset | Lucene ref | ZBSearch nDCG@10 | Orama nDCG@10 | ZBSearch ms/query | Orama ms/query |
| --- | ---: | ---: | ---: | ---: | ---: |
| SciFact | 0.665 | **0.675** | 0.324 | 0.5 | 4.9 |
| NFCorpus | 0.325 | **0.309** | 0.212 | 0.1 | 0.6 |
| ArguAna | 0.414 | **0.327** | 0.130 | 2.9 | 48.2 |
| **Macro average** | - | **0.437** | 0.222 | 2.1 | 34.3 |

ZBSearch's BM25 lands close to the Lucene reference on SciFact (above it) and NFCorpus, while Orama scores about half of ZBSearch's macro average - at roughly **16× the per-query latency**. Full per-engine tables (including MiniSearch, FlexSearch, Lunr, and Fuse.js) are on the [benchmarks page](/benchmarks).

### ZBSearch IVF vs Orama flat

ZBSearch adds an optional [IVF index](/docs/zbsearch/usage/create#choosing-an-ivf-index) for approximate nearest-neighbor search. Orama does not ship an equivalent in the JS core.

| Benchmark | Orama 3.1.18 (flat) | ZBSearch 4.0.2 (flat) | ZBSearch 4.0.2 (IVF) |
| --- | ---: | ---: | ---: |
| Vector search | 2,206 ops/s | 2,636 ops/s | **14,266 ops/s** |
| Strict similarity | 4,120 ops/s | 6,563 ops/s | **17,377 ops/s** |
| Vector + filters | 5,180 ops/s | 5,939 ops/s | **18,708 ops/s** |

With IVF (`nlist=179`, `nprobe=16`), ZBSearch vector search runs at **3.6–6.5×** the throughput of Orama's flat index on this dataset.

## Inverted index (postings)

Starting in **3.3.0**, ZBSearch stores full-text doc IDs in explicit **posting lists** outside the radix tree dictionary. The radix tree handles prefix navigation and typo tolerance; postings map each token to its document IDs.

This removes duplication that existed between inline radix `Set`s, `tokenOccurrences`, and scattered serialization of doc ID arrays. On save, posting lists are **delta-encoded** (sorted doc IDs stored as gaps), which shrinks the bundle without changing search semantics.

At runtime, document frequency for BM25 is derived directly from posting list length - no separate counter map is maintained. Leaf nodes also keep a direct reference to their posting array so inserts can append without a map lookup on every token.

## Memory footprint

Measured in isolated Node.js processes with `--expose-gc`, after indexing all **1,512** records and running **100** warmup searches. **Heap delta** is the increase over a GC'd baseline after the index is built - the most apples-to-apples comparison.

| Metric | Orama 3.1.18 | ZBSearch 4.0.2 | Difference |
| --- | ---: | ---: | --- |
| Indexed heap delta | 14.54 MB | 11.28 MB | ZBSearch **22.4%** lower |
| Search heap delta (100 queries) | 138 KB | 240 KB | Orama **42.5%** lower |

The savings come from the index structure itself. ZBSearch's search working set is slightly larger because it keeps reusable typed-array scoring buffers (about 12 bytes per document) instead of allocating a new map on every query.

## Persistence size

Serializing the same indexed dataset produces a much smaller bundle with ZBSearch 4.0.2:

| Engine | JSON | GZIP |
| --- | ---: | ---: |
| Orama 3.1.18 | 5,180,851 bytes | 1,295,034 bytes |
| ZBSearch 4.0.2 | 3,009,835 bytes | 838,890 bytes |
| Difference | **41.9% smaller** | **35.2% smaller** |

Delta-encoded postings and dropping redundant `tokenOccurrences` from the serialized snapshot account for most of the reduction. v4 also adds a [chunked persistence format](/docs/zbsearch/usage/serialization) for indexes that outgrow a single string.

## Run the benchmarks yourself

From the repository root, build ZBSearch first, then run any suite in `benchmarks/`:

```bash
cd packages/zbsearch && npm run build
cd ../../benchmarks && npm install

npm run benchmark:compare      # Orama vs ZBSearch head-to-head
npm run benchmark              # core insert/search
npm run benchmark:algorithms   # BM25 vs QPS vs PT15
npm run benchmark:facets       # facet workloads
npm run benchmark:vector       # vector search (flat)
npm run benchmark:vector-ivf   # vector flat vs IVF
npm run benchmark:bkd          # geosearch BKD tree
npm run benchmark:avl          # sorted AVL tree
npm run benchmark:bundle-size  # serialized DB size
npm run benchmark:memory       # in-memory heap footprint
npm run benchmark:search-quality # BEIR ranking quality
```

Results are saved as JSON and HTML charts under `benchmarks/benchmark/results/`.
